# findex (v1.0.0)

**Live Service URL:** `https://findex-search.onrender.com` (або `http://localhost:8000`)

## Головні показники продуктивності
* **Розмір корпусу:** 10,000+ документів
* **Затримка (p95):** 2.1 ms (на 4 воркерах Uvicorn)
* **Максимальне прискорення (NumPy BM25):** 3.8x у порівнянні з чистою реалізацією на Python

---

## Схема шляху даних (Architecture Pipeline)
`Корпус (HTML/TXT) -> Crawl/Scrape (selectolax) -> Tokenizer -> Inverted Index -> NumPy Scorer (BM25/TF-IDF) -> FastAPI REST API -> Jinja2 UI`

## Зведені вимірювання (Лабораторні роботи 1–8)

### Лабораторна робота 8: Оптимізація та NumPy

| Запит / Сценарій | BM25 Python (ms) | BM25 NumPy (ms) | Прискорення (Speedup) |
| :--- | :---: | :---: | :---: |
| **Частий терм ("python")** | 12.4 | 3.1 | **4.0x** |
| **Рідкісний терм ("fastapi")** | 2.1 | 1.8 | **1.17x** |
| **Мульти-терм ("python search index")** | 24.8 | 6.5 | **3.8x** |

#### Пояснення результатів:
* **Найбільший виграш:** Досягається на частих термах та багатослівних запитах, оскільки обчислення BM25 виконуються масивами NumPy на рівні нативного C-коду (`np.add.at`, `np.argpartition`), минаючи накладні витрати циклів Python.
* **Малий виграш:** На рідкісних термах довжина списку постінгів дуже мала, тому накладні витрати на створення обгортальних масивів `np.array` нівелюють перевагу векторного обчислення.
